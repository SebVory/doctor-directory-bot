# Agent rules — doctor-directory-bot

## Never read `data.json` directly

`data/full-snapshot/data-snapshot.json` is ~3.1 MB of dense JSON (7029 records). Reading it into context costs
roughly **0.8–1M tokens** — more than a whole session's budget, for a file whose
shape fits in ten lines.

Never `Read`, `cat`, `head`, `tail` or `grep` over `data/full-snapshot/*`, and
never pass it to a tool that returns its contents.

**Do this instead** — let node do the work and print only the aggregate:

```bash
node -e "const d=require('./data/full-snapshot/data-snapshot.json');
  console.log('rows', d.length);
  console.log([...new Set(d.map(r=>r.speciality))].sort());"
```

The rule is about what lands in the context window, not about touching the file.
A script that reads 3 MB and prints 10 lines is fine. A tool call that returns
3 MB is not.

## Use the sample for anything needing real rows

`data/data-sample.json` (500 rows, generated by `npm run sample`) is a stratified
slice that keeps every speciality, location, language and surname, plus the
known-hard rows. Tests read it. Regenerate with the script — never hand-edit it,
or it stops being representative.

It is still ~256 KB (~75k tokens), so the same rule applies: aggregate it with
node, do not `cat` it into the conversation.

Positional slices are not a substitute, and this was measured rather than assumed:
a lead cut of the file missed 9 of 42 towns, and a middle cut missed Psychiatry —
the speciality in the flagship "two Dumitrescu in Kluž" case. Coverage has to be
constructed, not hoped for. Both cuts were deleted; do not reintroduce that shape.

`SNAPSHOT_FILE` overrides what `npm run mock-api` serves and what `npm run sample`
reads; both default to the full snapshot.

## Three kinds of test data — do not mix them

| What | Where | Input | Answers |
|---|---|---|---|
| Synthetic fixtures | `fixture()` in `tests/` | generated rows | do the ingest guards fire? |
| Representative sample | `data/data-sample.json` | real rows, stratified | what is the real-world hit rate? |
| Behavioural evals | `evals/cases.json` | Czech utterances | does the bot ask, confirm, refuse correctly? |

Hard cases belong in `evals/cases.json` as utterances, **not** as curated rows in a
data file. A data file stuffed with only hard cases makes every score meaningless —
difficulty and representativeness are separate axes and need separate files.

## Where the reasoning lives

`DECISIONS.md` records what was measured, what it showed and what was decided
because of it — including ideas that were measured and rejected. Add to it when a
decision rests on a number rather than on taste, and keep the number in the entry.
Commit messages carry the same reasoning for the change they ship.

## Project conventions

- ESM, `strict` + `noUncheckedIndexedAccess`. No `any`, no non-null `!`.
- Nothing calls the hospital endpoint during a call. Reads go to the SQLite snapshot.
- The agent reaches data only through tools — never raw SQL from a prompt.
- Dependencies are deliberately few: `@anthropic-ai/sdk`, `better-sqlite3`, `zod`,
  `dotenv`, plus `tsx`/`typescript`/`vitest` for development.
- `npm test` and `npm run typecheck` are free and offline. Use them by default.
- Every billed eval run goes in `evals/RUNS.md` with its score, its failures and
  what each failure was caused by, so the same question is never paid for twice.
- **`npm run evals` and `npm run doctor` bill a real Anthropic API key. Never run
  them without asking first, every time.** State how many calls a run will make
  before asking — a benchmark of "3 models x 3 runs x 3 cases" is ~70 billed calls,
  not one task. To verify loop or history logic without spending anything, inject a
  fake client: `runTurn(utterance, history, { client })`.
